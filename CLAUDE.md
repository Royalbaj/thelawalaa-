# Thelawalaa — project notes for Claude Code

Multi-role street-food ordering app. **Launch market: Banepa–Godam Chowk, Kavrepalanchok, Nepal.**
Stack: Next.js 15 (App Router) + React 19 + TypeScript, Supabase (Postgres/RLS/Auth), Tailwind, Resend, Vercel.

## First steps after unzipping
1. `npm install`
2. Copy `.env.example` → `.env.local` and fill in Supabase + Resend + OTP_HMAC_SECRET values (see README §2).
3. Create a Supabase project, then apply `supabase/migrations/001_initial_schema.sql` and `supabase/seed.sql` (see README §1).
4. `npm run dev`

## Roles
customer · super_admin · pos_user · delivery_driver · accountant. Route protection is in `middleware.ts`.
`super_admin` is the management role (migration 018 restored it after 014 had merged it into `admin`;
`admin` stays allowed by the DB constraint but no code grants it anything). Counter work and management
are separate logins: `pos_user` gets only the POS screen, `super_admin` never sees it. `accountant` only
exists to log into the separate Accounts app and has no access to the main site — signing in
there (or opening any staff page) sends them to `accounts.thelawalaa.com/login?from=main`
(`ACCOUNTS_LOGIN` in `lib/role-home.ts`); the two sites don't share a session.
**A role rename must land in the DB, `middleware.ts` ROLE_ROUTES, every `requireRole()`, `lib/role-home.ts`
and the Accounts app together, and be deployed** — a half-applied rename (DB changed, production code not)
locked every manager out in Sep 2026.

## Apps in this repo
- **Main site** (this directory) — customer site, POS (`/admin`), management (`/admin/(mgmt)/*`),
  driver portal (`/delivery`), staff training (`/staff`). Deploys as the `thelawalaa` Vercel project.
- **`accounts-app/`** — a fully separate Next.js project (own `package.json`, own Vercel project,
  own middleware/login) at `accounts.thelawalaa.com`: a simple money book the manager keeps BY HAND —
  money in / money out entries with a category, note, payment method (cash/bank/QR) and an optional
  bill photo/PDF, plus a dashboard (balance left, today/week/month, charts), reports with Excel/CSV/print,
  and stock. It deliberately does NOT read sales from `orders` (the owner's call — sales are typed in).
  Shares the Supabase project; deployed independently. Restricted to `super_admin`/`accountant`.
  Its Vercel project's Root Directory must be `accounts-app` — with `.` it builds the customer site
  (it did until 2 Oct 2026; set via `vercel project update accounts-app --root-directory accounts-app`).
  The main `thelawalaa` project's Root Directory must stay `.` (automatic). On 2 Oct 2026 it ended up as
  `accounts-app` as well, right after that change, and promoting the next build put the Accounts login on
  www.thelawalaa.com for ~3 minutes. After ANY Vercel settings change, run `vercel project inspect` on BOTH
  projects, and before promoting a main-site build, check its URL actually serves the customer site.

- **`ad-video/`** — the brand ad, made in code with Remotion (own `package.json`, never deployed,
  excluded from the root `tsconfig.json` so `next build` never type-checks it). `npm run render` there
  makes the 9:16 Reel and 4:5 Feed MP4s in `ad-video/out/`; its prices/menu text are copied from the
  live menu, so re-check them when the menu changes. On-screen text is Nepali; the soundtrack (madal/bansuri
  folk-pop) is synthesised by `scripts/make-music.mjs`, timed to the cuts in `src/Ad.tsx`; the Nepali
  voiceover (`scripts/make-voice.py`, Microsoft ne-NP neural voice) is mixed in by `scripts/mix.mjs`, and its
  word timings place the on-screen words (`src/voice.ts`). A second, creator-style countdown ad lives in `src/ugc/` (female voice via
  `scripts/make-voice-ugc.py`; its `public/voice-ugc/timeline.json` drives the cuts, captions and sound effects — no music, the
  owner's call), and a chat-story skit in `src/chat/` (story + timing in `scripts/make-chat.mjs`). Momo is
  said and written "मोमो"; delivery nearby is FREE, on the website and in the ads alike.
  The brand film "यो आवाज याद छ? — ठेलावाला आयो!" is `src/film/` (timing in `scripts/film-script.json`; its voice can be a
  guide TTS, a person's phone recording via `scripts/place-recording.mjs`, or ElevenLabs via `scripts/make-voice-eleven.mjs`).
  The voice-note chat skit is `src/vchat/` (`npm run vchat`); a shoot kit for real-people videos is `out/shoot-kit.html`
  (published privately as an artifact). The meme "नेपालीले मात्र बुझ्छन्" is `src/meme/` (`npm run meme`); stock footage
  and its licences are in `ad-video/public/stock/CREDITS.txt` — only Mixkit FREE-licence clips (Restricted = non-commercial).

## Conventions / guardrails (please preserve)
- ALL mutations go through server actions in `app/actions/*` — they start with `requireRole(...)` and are Zod-validated. Clients never write orders or payment status directly.
- Privileged reads use the service-role client in `lib/supabase/admin.ts` (guarded by `import "server-only"`), only after a role check.
- Payments are hybrid: cash/QR-in-person orders start `payment_status:'pending'` and only an admin can flip them to paid via `markOrderPaid` (audited, actor = the admin) — UI shows "Collect Rs X". Online orders paid via the eSewa gateway (`lib/payments/esewa.ts`, `app/actions/payments.ts`) are auto-confirmed by the `app/api/payments/esewa/callback` route once it re-verifies the transaction server-side against eSewa's status API — that audit row has `actor_id: null` ("the system"), never trust the redirect payload alone.
- **eSewa and delivery are both gated behind a single-row `app_settings` table** (`esewa_enabled`, `delivery_enabled`, both default `false`), toggled only from `/admin/settings` via `updateAppSettings` (`app/actions/settings.ts`, `super_admin` only). Checked both in the UI (`app/order/page.tsx`, homepage) and server-side in `createOrder`/`getEsewaPaymentForm` — never trust the client alone for whether a gated payment/order type is currently allowed.
- The opening-day promo (`app_settings.opening_promo_*`, `lib/promo.ts`) overrides a category's price both at charge time (`createOrder`/`createPosOrder`) AND everywhere it's displayed (POS tiles, `/order`, homepage) — if you add a new place a product price is shown, run it through `applyOpeningPromoPrice()` too, or the shown price will drift from what's actually charged.
- Currency: `npr()` in `lib/utils.ts`. Phone validation is Nepali (`lib/validations/auth.ts`).
- Delivery: FREE (owner's call, 6 Oct 2026 — `createOrder` writes `delivery_fee: 0`; the 3 earlier orders that paid Rs 20 keep it, so `orders.delivery_fee` is still shown in order details / Excel when it's above 0) within the delivery area set in Admin → Settings → Delivery area (migration 033: `app_settings.delivery_radius_km`, default 5, and the shop's `store_lat/lng`, set from a device in the shop; `deliveryArea()` / `outsideArea()` in `lib/geo.ts`, falling back to lib/seo.ts's approximate spot). A shared pin — or a saved address with one — outside it can't order delivery online: checkout shows "We're not delivering to this location right now" with Call (the Website-text WhatsApp number, `telHref`/`phoneDisplay` in `lib/utils.ts`), WhatsApp and Switch to pickup, and `createOrder` refuses it too. Typed addresses without a pin can't be measured, so they're allowed. Website wording that says "5 km" is editable text — update it if the radius changes.
- Business facts + SEO live in ONE place: `lib/seo.ts`. FAQs in `lib/faqs.ts`.
- Delivery code (OTP): 2 digits (owner's call — 3 wrong tries lock it, then the shop confirms), derived from the order id with `OTP_HMAC_SECRET` (`lib/delivery-otp.ts`), only its HMAC stored. The customer sees it in the order-placed toast, on `/track` (the API returns it ONLY to the signed-in owner — riders know order ids; a guest's copy lives in that tab's sessionStorage, `lib/guest-order.ts`) and in their email. Never expose customer phones in driver HTML: `lib/driver-jobs.ts` is the only shape rider screens get (first name, items, address/pin, amount to collect), and Call fetches the number on tap (`getCustomerTelLink`, guest numbers come from the notes header).
- Orders show as THREE steps — Ordered → Confirmed → Ready to collect (delivery: → On the way) — via `lib/order-status.ts`. The DB keeps its wider status set (`preparing`, driver states) and those fold into the nearest step; never print a raw `orders.status`, always `orderStatusLabel()`. (The Accounts app no longer shows orders, so there's no copy of it there any more.)
- `/admin` (root) is the POS terminal, in its own `app/admin/(pos)/` route group with a minimal, sidebar-free layout — pos_user needs the screen space. Management pages live under the `app/admin/(mgmt)/` route group, which adds the sidebar shell and is `super_admin`-only. There is deliberately NO `app/admin/layout.tsx`: a layout there wraps both groups, so any role gate in it locks one of them out. Don't move a page out of `(mgmt)` without checking whether pos_user should actually see it.
- `orders` RLS has one broad staff policy (`public.get_my_role() IN ('pos_user','admin','super_admin')`) — this is what Realtime `postgres_changes` subscriptions check (Live Orders panel, dashboard feed). The service-role page-load fetch always sees everything regardless, so a missing/narrow RLS policy here fails silently: initial load looks fine, new orders just never show up live. If live orders stop updating again, check this policy AND that `orders`/`deliveries` are still in the `supabase_realtime` publication (`select * from pg_publication_tables`) — it was found empty in Sep 2026 (migration 019). The Live Orders panel also re-syncs every 20s via `getLiveOrders()` as a safety net.
- Supabase cookies use the getAll/setAll pattern in `middleware.ts` and `lib/supabase/server.ts`: a refreshed session is written to the request AND the response, so long-open devices (the POS iPad app) don't drop their sign-in. Don't go back to get/set/remove.
- The POS stays signed in for 24 hours after a password sign-in (`components/pos/pos-session.tsx`, from `user.last_sign_in_at`), through app closes and iPad sleep; after that it asks again only when the app is opened or brought to the front (never mid-order) — `/auth/login?daily=1` explains why.
- Staff share devices. Sign out only via `signOutHere()` (`lib/sign-out.ts`: this device only + a full page load) and finish sign-in with `window.location.replace`, never `router.push` — Next's in-memory back/forward cache otherwise shows the previous user's screens on Back. Every signed-in layout renders `<SessionGuard userId={profile.id} />`; keep it on new ones.
- POS deals — Student 5% OR Member price OR Staff, only one per order (`lib/discounts.ts`, shared by the POS screen and `createPosOrder`, which recomputes everything; the screen only asks). Student: 5% off items with `products.student_discount_eligible` (Coca-Cola is off by default), whole rupees. Member: items with `products.member_price` (every momo is Rs 99, migration 022; set per item in Admin → Menu) charge that instead. Staff (migration 035): up to `app_settings.staff_free_items` items cost Rs 0 — set in Admin → Settings → Staff sale (`updateStaffSale`, 0–20, 0 hides the button); `staffFreeItems()` frees the dearest first, never membership cards, and charges anything over the limit; tiles show Rs 0 while free items are left. Order lines keep the normal price either way; the saving is `orders.discount_amount` + `discount_label` ("Student 5%" / "Member price" / "Staff"). Staff free items show in the POS "Today" sheet under Discounts given and are left out of Marketing's "offers given" (a staff cost, not an offer).
- `products.pos_only` items show on the POS but never on the website: every public product query filters `pos_only = false`, and `createOrder` refuses them for non-staff. Any new public menu query needs the same filter.
- New-online-order alerts on the POS device (main device: an iPad 6th gen): an in-page chime (`lib/order-sound.ts` — iPad Safari only allows sound after a tap, so every tap re-unlocks it) plus Web Push (`lib/push.ts`, `public/sw.js`, sent from `createOrder` via `after()`). iOS delivers Web Push only to the POS installed to the Home Screen (`public/pos.webmanifest`, start_url `/admin`); the bell in the POS header walks staff through it. Needs the VAPID env vars (Vercel has them; `.env.local` doesn't).
- The POS layout (`components/pos/pos-workspace.tsx`): Sell / Orders tabs below 1280px (phone, iPad portrait and the 1024px landscape), side by side above; both panels stay mounted. Check new POS UI at 375, 768, 1024 and 1440px — and at a SHORT phone height too (375×548 is an iPhone SE in Safari): the cart's footer (total, cash return, Place order) is pinned and everything above it scrolls, so it can never be pushed off-screen. The POS layout sets `viewportFit: "cover"` and `PosThemeRoot` pads by the safe-area insets (home bar / notch on the installed app).
- ONE navigation per screen, switching at `md`: below it the floating bottom bar (`components/mobile-nav.tsx`, website + customer portal), from `md` the top links (`components/navbar.tsx`) / account tabs (`components/account/account-nav.tsx`). Phones never get a hamburger as well — the admin's "More" tab opens its menu, the driver app has only its bottom tabs. `useViewerRole()` (`lib/use-viewer.ts`) is the one role lookup both bars share. The bottom nav brings its own spacer; never put bottom padding for it on `<body>` — that gave every staff screen (no nav) a blank strip and made the whole POS scroll on iPhones.
- End of shift (POS header → "Today" — also shows today's average serving and kitchen-ready time, `components/pos/day-sales-sheet.tsx`, maths in `lib/day-sales.ts`): today's (Nepal day) or this shift's sales as Reports counts them (paid, not cancelled), by payment method and counter/online, plus checks (handed over but unpaid, paid-then-cancelled, open over an hour, un-marked "paid"). Cash expected = opening float + CASH orders whose payment landed in the period (`paid_confirmed_at`, or `created_at` for POS orders, which are paid on the spot). "Close shift" (`closeShift`) recomputes that server-side and saves the ONE total the counter types ("Total cash now" — the owner doesn't want a note-by-note count) as an audit row `SHIFT_CLOSE`; the next shift starts from it, and Admin → Dashboard lists the day's closes with over/short.
- POS cancelling is a switch: `app_settings.pos_can_cancel` (migration 034, default true), Admin → Settings → Feature flags "Counter (POS) can cancel orders". When off, the Live Orders panel hides Cancel (`canCancel` prop from the POS page) and `adminUpdateOrderStatus` refuses `cancelled` from a pos_user; super_admin can always cancel (Admin → Orders).
- Admin → Reports Excel (`lib/sales-report-excel.ts`, route only streams it): Summary (best day, average per selling day), a "Daily sales" sheet (best day green, today yellow, Saturdays shaded, data bars, SUM totals), Orders grouped under a highlighted bar per day with that day's paid total (cancelled struck through, unpaid amber), Products ranked. Keep daily sales the highlight.
- Cash at the POS: "Cash received" is optional; when entered, the cart shows the return amount and the "Order placed" popup shows Received + Return (in big type) next to the order number.
- The POS is ALWAYS dark (owner's call — no switch; `app/admin/(pos)/layout.tsx` passes `initialDark`). Tailwind `darkMode: "selector"`, so `dark:` classes only apply inside a `.dark` wrapper: the POS, the driver app (dark-only styles), and Staff Training, which has a light/dark switch in its header (`components/theme-toggle.tsx`, cookie `staff-theme`, default light) plus a footer with an Online/Offline line — style new training UI for both.
- `pos.thelawalaa.com` serves this same app (Vercel domain on the `thelawalaa` project); its `/` redirects to `/admin` and it's `noindex` (`next.config.mjs`). A browser keeps ONE sign-in per address for all its tabs (and `SessionGuard` refreshes tabs when it changes), so the counter signs in there while a manager/rider stays signed in on www in another tab. Cookies must stay host-only (never set a cookie `domain`) or the two would merge. Emails/invites still link to www.
- Sales archives (the opening-day reset) download as Excel from `/admin/archives/[id]/excel` (`lib/sales-archive-excel.ts`, built on demand from `sales_archives.snapshot`); Admin → Settings lists them all.
- SQL functions called through the API (`supabaseAdmin.rpc`) run under pg-safeupdate: every UPDATE/DELETE needs a WHERE (`WHERE true` is fine) or it fails with "UPDATE requires a WHERE clause".
- Staff training (`/staff`, `components/staff/unskippable-video.tsx`): YouTube IFrame API — the CSP in `next.config.mjs` must allow www.youtube.com in `script-src` AND `frame-src` or the player never loads. Skipping is blocked by only crediting what's been watched at real speed (seeks/fast-forward snap back, playback rate is held at 1×, and YouTube's "ended" only counts if it was really watched). Training is per PERSON, not per login (the POS login is shared; migration 028): Admin → Staff Training → Team & PINs adds each staff member with their own 4-digit PIN (hashed via `lib/accounts-pin.ts`, unique among active people) and the videos they must watch (`training_assignments`; a new video can go to everyone). On `/staff` they type the PIN (`unlockTraining`, 5 wrong tries/15 min, audit `TRAINING_PIN_FAIL`), which sets a 3-hour httpOnly HMAC cookie bound to the login (`lib/training-pin-cookie.ts`); they see only their videos and finishes go to `training_people_progress` (+ audit `TRAINING_COMPLETED`). "Not you? Switch" clears it. Admins see who has/hasn't finished on Admin → Training and the dashboard card (`lib/training-status.ts`). The old per-login `staff_training_progress` table is no longer used.
- Accounts app security: sign-in (super_admin/accountant) THEN a person's own 4-digit PIN. People live in `account_users` (migration 024) — the admin adds/renames/re-PINs/switches them off in Admin → Staff & Users → Accounts people (`app/actions/accounts-people.ts`, hashes via `lib/accounts-pin.ts`, a copy of `accounts-app/lib/pin.ts`). The PIN alone identifies the person, so active PINs must be unique (checked on every add/change; switching someone back on needs a new PIN). 5 wrong tries in 15 min locks the PIN screen (`audit_logs`). Unlocking sets an httpOnly HMAC cookie naming the person and bound to the login (`accounts-app/lib/pin-cookie.ts`, key derived from the service-role key); `requireAuth()` returns `{ user, profile, person }` and every entry / stock change stores `entered_by`/`edited_by` = that person. Ledger + stock tables have RLS on with no policies — service role only, after `requireAuth()`. Bills: PRIVATE `account-bills` bucket, only ever opened via `/bills/[id]` (2-minute signed link). Accountant logins are refused on the main site's login (they only work on accounts.thelawalaa.com).
- Accounts speed: the middleware runs at the edge, far from the database (us-east-1), so it does NO database round trip for an unlocked user — `getClaims()` verifies the sign-in token locally (project signs with ES256) and a valid unlock cookie (only issued after the full role check) skips the role lookup; pages/actions still run the full `requireAuth()` next to the database, cached once per request with React `cache()`. `(app)/loading.tsx` answers every tap instantly and `staleTimes.dynamic = 30` keeps recently seen tabs. Keep new per-request work in pages (the layout only re-renders on refresh).
- Stock follows the POS (migration 024): a stock item is counted at `counted_at`; `stock_levels()` (SQL) = count + restocks − waste − POS/website sales of LINKED menu items (`stock_item_products.units_per_sale`) since then, cancelled orders excluded — nothing is decremented, so cancelling puts stock back. After every sale `checkStockAfterSale()` (`lib/stock-alerts.ts`, via `after()` in `createOrder`/`createPosOrder`) pushes ONE "Running low"/"Out of stock" alert per drop to staff devices (`stock_items.alert_state`; restock/count in Accounts resets it).
- Dates in both report screens are Nepal calendar days (`lib/dates.ts`; `accounts-app/lib/dates.ts` is the original — change both). Never bucket by the server's clock: Vercel is UTC, 5h45m behind Banepa.
- Charts (Admin → Reports, Accounts) use recharts with the validated pair blue `#2a78d6` / orange `#eb6834` (money in / money out; counter / online), bars ≤ 24px with rounded tops, a legend for 2+ series and a "Show as table" view. Admin → Reports (`lib/sales-report.ts`) counts sales as paid, not-cancelled orders; POS orders are the ones with `placed_by` set.
- Tagline everywhere: "Where flavour meets hygiene" (logo component, loader, email layout + `public/images/email/logo.png`, Supabase backup templates). The hero/packaging PHOTO still shows the old printed tagline.
- Branding: the name at the top of any screen is `<BrandLogo>` (`components/brand-logo.tsx` — the orange→red "TW" tile + brown wordmark, cream on dark, optional `label` like "POS"/"Driver"), never plain or gradient text. App icons/favicon are the same TW tile (rendered in headless Chrome with Poppins, like `public/images/email/*`). Loading: `components/brand-loader.tsx` (`BrandSplash` in `app/loading.tsx`, `BrandLoader` in each portal's `loading.tsx`) — animations in `globals.css` (`tw-*`), shown only after 180ms.
- Consent (migration 029): nobody is opted in to offers by default. Sign-up requires ticking the Terms and has an UNticked "send me offers" box; customers join/leave from the account home card, Profile → Messages from us (`setMarketingOptIn`) or the email unsubscribe link (`/unsubscribe`, `unsubscribeByLink` — signed with `lib/signed-links.ts`, can only switch offers OFF, so it's the second mutation without `requireRole`). `profiles.marketing_opt_in/_at` and `terms_accepted_at` are server-written only (the privilege-guard trigger resets them on a user's own update). `/terms` (incl. offers can change/end without notice, privacy) is editable in Admin → Website text ("Terms & Conditions" section); bump `terms.updated` when changing it.
- Marketing (Admin → Marketing & ROI, migration 032 — replaced 031's ad tracking at the owner's request: it's a budget + ledger, NOT ad/link tracking). `marketing_budgets` (month × 'total' or a category), `marketing_entries` (kind expense|return, date, category, optional activity, amount, payment method for expenses, new customers for returns, note), `marketing_activities` (named efforts with their own budget/dates/status — e.g. "Membership Card") and `marketing_settings` (gross margin %). All RLS on, no policies; actions in `app/actions/marketing.ts`, numbers in `lib/marketing.ts`, labels/maths in `lib/marketing-shared.ts`. Returns are typed in by hand; ROI = (returns − spent) ÷ spent, "ROI on profit" counts returns at the margin. Shop sales (paid, not cancelled) appear only as "marketing ÷ sales"; "offers given" (discounts, points, free items from orders) is shown but not part of the budget. Month view via `?month=YYYY-MM`; CSV at `/admin/marketing/export`. The ROI planner (`roi-calculator.tsx`) is for trying an idea before spending.
- POS stock is look-only: `getPosStock()` returns EVERY stock item (`all`, plus `warnings` for low/out and `byProduct`), every linked menu tile shows "N left" (grey OK / amber low / red out), and the POS header's "Stock" sheet lists them all. Counting and restocking stay in the Accounts app.
- Notifications (migration 029): Admin → Notifications writes `notifications` (audience customers|drivers, RLS on, no policies). Customers see them only if opted in (`/account/notifications`, bell in the account header); drivers in `/delivery/updates`; unread = newer than `profiles.notifications_seen_at` (`lib/notifications.ts`, marked read by `MarkSeen` on view). Customer messages can also email every opted-in, confirmed customer (Resend batch, `offerNoticeEmail` with a personal unsubscribe link); driver messages can push to riders' phones.
- Delivery location: checkout's "Share my current location" (browser geolocation) sends a pin, validated to Nepal (`orderSchema.delivery_location`); `createOrder` stores `orders.delivery_address/_lat/_lng/_accuracy_m`. No pin → the typed address must be ≥10 chars. Saved addresses can carry a pin (`addresses.lat/lng`). Maps: `lib/geo.ts` (Google Maps directions/search links, and the keyless `output=embed` map the CSP's frame-src already allows); distances use the APPROXIMATE shop coords in `lib/seo.ts`.
- Driver app (`/delivery`): Deliveries (online switch, one card per job with embedded map, Navigate, Call, step buttons, delivery-code entry) · History · Updates · Me (phone alerts, training, sign out). Installable (`public/delivery.webmanifest`); `assignDriver` pushes "New delivery" to that rider (`pushToDrivers` in `lib/push.ts`; device side shared with the POS bell in `lib/push-client.ts`). Admin → Deliveries shows address/pin/items and can assign online or offline riders.
- Prices disappear once an order is done (delivered/cancelled): `/api/track` nulls them, customer order history shows items only, rider history shows no amounts at all. Admin → Orders shows every order's items plus a "details" breakdown (`components/admin/order-details.tsx`); Admin → Leaderboard ranks signed-in customers by paid, not-cancelled orders or spend.
- Guests leave nothing on a shared phone: the cart is per tab (`sessionStorage`, old `localStorage` carts are cleared), guest name/phone/address fields have `autoComplete="off"`, checkout `router.replace`s to tracking, and signing out clears sessionStorage. Signed-in customers aren't asked their name at checkout (the account's is used; staff using /order still type one).
- Customer feedback: public `/feedback` (`components/feedback-form.tsx`; linked from the footer and the order-tracking page with `?order=`) → `feedback` table (migration 025, RLS on, no policies). `submitFeedback` (`app/actions/feedback.ts`) is one of only two mutations without `requireRole` (the other is `unsubscribeByLink`) — it's Zod-validated, has a honeypot, and throttles by a keyed hash of the IP (3 per 10 min, counted in the table). Read in Admin → Feedback (new-count badge in the menu, dashboard card).
- Admin panel on phones: below `lg` a bottom tab bar (Home · Orders · Menu · Reports · More) and the sidebar as a drawer; below `md`, lists are cards instead of tables (Orders, dashboard feed, Staff, Signups) — new admin lists should do the same. `app/globals.css` keeps every input ≥16px on phones (iPhone zooms into smaller ones). Tailwind scans `lib/` too — `STATUS_COLORS` class names live only there.
- The main login answers an accountant's (correct) password with "Wrong email or password" — Accounts logins only work on accounts.thelawalaa.com, and the main site never hints that they exist.
- Visual style (owner's call — "no AI-looking icons"): no emoji anywhere in the UI or emails, and no decorative "icon in a pastel box" tiles. Use typography (thin orange rules, numbered 01–04 columns), real brand marks (`components/icons/brand-glyphs.tsx` — WhatsApp, Facebook, Instagram, TikTok), lucide icons only where they carry meaning (phone, map pin, navigation), and `components/stars.tsx` for ratings.
- Hero steam: `components/hero-steam.tsx` — a WebGL shader (domain-warped fbm, rising) over the momo, placed in the photo's 3:2 coordinates (left 50%, top 0, 46% × 52%), screen-blended, half resolution, ~30 fps, paused off-screen / hidden tab / reduced motion, absent without WebGL. If the hero photo changes, re-place it over the new steaming dish.
- Homepage hero: the product photo sits on an "ambient" backdrop made from its own blur placeholder (`heroImage.blurDataURL`, stretched + darkened) and fades out at its edges via `.hero-photo-fade` (CSS mask) — swap the photo and the backdrop follows.
