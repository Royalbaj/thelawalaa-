# Thelawalaa — project notes for Claude Code

Multi-role street-food ordering app. **Launch market: Banepa–Godam Chowk, Kavrepalanchok, Nepal.**
Stack: Next.js 15 (App Router) + React 19 + TypeScript, Supabase (Postgres/RLS/Auth), Tailwind, Resend, Vercel.

## First steps after unzipping
1. `npm install`
2. Copy `.env.example` → `.env.local` and fill in Supabase + Resend + OTP_HMAC_SECRET values (see README §2).
3. Create a Supabase project, then apply `supabase/migrations/001_initial_schema.sql` and `supabase/seed.sql` (see README §1).
4. `npm run dev`

## Roles
customer · super_admin · pos_user · delivery_driver · accountant. Route protection is in `middleware.ts`.
`super_admin` is the management role (migration 018 restored it after 014 had merged it into `admin`;
`admin` stays allowed by the DB constraint but no code grants it anything). Counter work and management
are separate logins: `pos_user` gets only the POS screen, `super_admin` never sees it. `accountant` only
exists to log into the separate Accounts app and has no access to the main site — signing in
there (or opening any staff page) sends them to `accounts.thelawalaa.com/login?from=main`
(`ACCOUNTS_LOGIN` in `lib/role-home.ts`); the two sites don't share a session.
**A role rename must land in the DB, `middleware.ts` ROLE_ROUTES, every `requireRole()`, `lib/role-home.ts`
and the Accounts app together, and be deployed** — a half-applied rename (DB changed, production code not)
locked every manager out in Sep 2026.

## Apps in this repo
- **Main site** (this directory) — customer site, POS (`/admin`), management (`/admin/(mgmt)/*`),
  driver portal (`/delivery`), staff training (`/staff`). Deploys as the `thelawalaa` Vercel project.
- **`accounts-app/`** — a fully separate Next.js project (own `package.json`, own Vercel project,
  own middleware/login) at `accounts.thelawalaa.com`: a simple money book the manager keeps BY HAND —
  money in / money out entries with a category, note, payment method (cash/bank/QR) and an optional
  bill photo/PDF, plus a dashboard (balance left, today/week/month, charts), reports with Excel/CSV/print,
  and stock. It deliberately does NOT read sales from `orders` (the owner's call — sales are typed in).
  Shares the Supabase project; deployed independently. Restricted to `super_admin`/`accountant`.
  **Running cost** (`/running`, also a tab beside Reports; migration 048): trading income (day sales …) against running costs, leaving
  out one-off setup buys and owners'/lenders' money — `account_categories.is_operating` (the "Running cost / Trading income / Not counted"
  switch per category in Settings; Owner investment, Loan received, Owner withdrawal and Equipment start off) and a per-entry override
  `account_transactions.one_off` (true = one-off, false = counted, NULL = the category decides; `isOperating()` / `runningCost()` in
  `lib/ledger.ts`). The page: a quick "Add a day's sales" form, income / cost / what's left / sales needed a day, the per-day verdict,
  the chart, by-category lists, the biggest money out with a Running cost / One-off switch each (`setEntryOneOff`), and what's left out.
  Its Vercel project's Root Directory must be `accounts-app` — with `.` it builds the customer site
  (it did until 2 Oct 2026; set via `vercel project update accounts-app --root-directory accounts-app`).
  The main `thelawalaa` project's Root Directory must stay `.` (automatic). On 2 Oct 2026 it ended up as
  `accounts-app` as well, right after that change, and promoting the next build put the Accounts login on
  www.thelawalaa.com for ~3 minutes. After ANY Vercel settings change, run `vercel project inspect` on BOTH
  projects, and before promoting a main-site build, check its URL actually serves the customer site.

## Conventions / guardrails (please preserve)
- ALL mutations go through server actions in `app/actions/*` — they start with `requireRole(...)` and are Zod-validated. Clients never write orders or payment status directly.
- Privileged reads use the service-role client in `lib/supabase/admin.ts` (guarded by `import "server-only"`), only after a role check.
- Payments are hybrid: cash/QR-in-person orders start `payment_status:'pending'` and only an admin can flip them to paid via `markOrderPaid` (audited, actor = the admin) — UI shows "Collect Rs X". Online orders paid via the eSewa gateway (`lib/payments/esewa.ts`, `app/actions/payments.ts`) are auto-confirmed by the `app/api/payments/esewa/callback` route once it re-verifies the transaction server-side against eSewa's status API — that audit row has `actor_id: null` ("the system"), never trust the redirect payload alone.
- **eSewa and delivery are both gated behind a single-row `app_settings` table** (`esewa_enabled`, `delivery_enabled`, both default `false`), toggled only from `/admin/settings` via `updateAppSettings` (`app/actions/settings.ts`, `super_admin` only). Checked both in the UI (`app/order/page.tsx`, homepage) and server-side in `createOrder`/`getEsewaPaymentForm` — never trust the client alone for whether a gated payment/order type is currently allowed.
- The opening-day promo (`app_settings.opening_promo_*`, `lib/promo.ts`) overrides a category's price both at charge time (`createOrder`/`createPosOrder`) AND everywhere it's displayed (POS tiles, `/order`, homepage) — if you add a new place a product price is shown, run it through `applyOpeningPromoPrice()` too, or the shown price will drift from what's actually charged.
- Currency: `npr()` in `lib/utils.ts`. Phone validation is Nepali (`lib/validations/auth.ts`).
- Delivery charge (owner's call, 11 Oct 2026, migration 042): Rs 20 when the FOOD (items subtotal, before vouchers/points) comes to less than Rs 99, free from Rs 99 — `app_settings.delivery_fee` / `free_delivery_from`, Admin → Settings → Delivery charge (`updateDeliveryCharge`; fee 0 = always free). `deliveryFeeFor()` in `lib/delivery-fee.ts` is shared by checkout (Food / Delivery / Total breakdown + "add Rs X more for free delivery") and `createOrder` (total = food − discounts + fee; vouchers and points never pay for delivery). The fee shows in the confirmation email, /track, Admin order details and the Excel. Website wording that mentions it ("free from Rs 99, Rs 20 below") is editable Website text / FAQs — update it if the numbers change; the ads still say delivery is free. Delivery is offered within the delivery area set in Admin → Settings → Delivery area (migration 033: `app_settings.delivery_radius_km`, default 5, and the shop's `store_lat/lng`, set from a device in the shop; `deliveryArea()` / `outsideArea()` in `lib/geo.ts`, falling back to lib/seo.ts's approximate spot). A shared pin — or a saved address with one — outside it can't order delivery online: checkout shows "We're not delivering to this location right now" with Call (the Website-text WhatsApp number, `telHref`/`phoneDisplay` in `lib/utils.ts`), WhatsApp and Switch to pickup, and `createOrder` refuses it too. Customers and guests can ONLY share a location (no typed or saved addresses, owner's call Oct 2026), so every website delivery is measured; only staff ordering on /order for someone else may type an address. Website wording that says "5 km" is editable text — update it if the radius changes.
- Business facts + SEO live in ONE place: `lib/seo.ts`. FAQs in `lib/faqs.ts`.
- The link-preview picture (Facebook / WhatsApp / Messenger) is `public/og.png` (1200×630, Oct 2026: "Banepa's Most
  Flavourful Chatpate & Momo · Godam Chowk, Banepa · Home delivery within 5 km · free from Rs 99"). The old one said
  Butwal — social sites cache it by URL, so when it's re-made, bump the `?v=` in `app/layout.tsx` and
  `components/structured-data.tsx`. It states the delivery terms: re-make it if they change.
- Delivery code (OTP): 2 digits (owner's call — 3 wrong tries lock it, then the shop confirms), derived from the order id with `OTP_HMAC_SECRET` (`lib/delivery-otp.ts`), only its HMAC stored. The customer sees it in the order-placed toast, on `/track` (the API returns it ONLY to the signed-in owner — riders know order ids; a guest's copy lives in that tab's sessionStorage, `lib/guest-order.ts`) and in their email. Never expose customer phones in driver HTML: `lib/driver-jobs.ts` is the only shape rider screens get (first name, items, address/pin, amount to collect), and Call fetches the number on tap (`getCustomerTelLink`, guest numbers come from the notes header).
- Orders show as THREE steps — Ordered → Confirmed → Ready to collect (delivery: → On the way) — via `lib/order-status.ts`. At the counter, POS orders (placed_by set) are ONE tap after the sale: Confirmed → Served/Collected, no "Ready" (owner's call; `nextCounterAction(status, type, counter)`); online orders keep Ready so customers know when to come. The serving-time trigger stamps ready_at = served_at for those. The DB keeps its wider status set (`preparing`, driver states) and those fold into the nearest step; never print a raw `orders.status`, always `orderStatusLabel()`. (The Accounts app no longer shows orders, so there's no copy of it there any more.)
- `/admin` (root) is the POS terminal, in its own `app/admin/(pos)/` route group with a minimal, sidebar-free layout — pos_user needs the screen space. Management pages live under the `app/admin/(mgmt)/` route group, which adds the sidebar shell and is `super_admin`-only. There is deliberately NO `app/admin/layout.tsx`: a layout there wraps both groups, so any role gate in it locks one of them out. Don't move a page out of `(mgmt)` without checking whether pos_user should actually see it.
- `orders` RLS has one broad staff policy (`public.get_my_role() IN ('pos_user','admin','super_admin')`) — this is what Realtime `postgres_changes` subscriptions check (Live Orders panel, dashboard feed). The service-role page-load fetch always sees everything regardless, so a missing/narrow RLS policy here fails silently: initial load looks fine, new orders just never show up live. If live orders stop updating again, check this policy AND that `orders`/`deliveries` are still in the `supabase_realtime` publication (`select * from pg_publication_tables`) — it was found empty in Sep 2026 (migration 019). The Live Orders panel also re-syncs every 20s via `getLiveOrders()` as a safety net.
- Supabase cookies use the getAll/setAll pattern in `middleware.ts` and `lib/supabase/server.ts`: a refreshed session is written to the request AND the response, so long-open devices (the POS iPad app) don't drop their sign-in. Don't go back to get/set/remove.
- The POS stays signed in for 24 hours after a password sign-in (`components/pos/pos-session.tsx`, from `user.last_sign_in_at`), through app closes and iPad sleep; after that it asks again only when the app is opened or brought to the front (never mid-order) — `/auth/login?daily=1` explains why.
- Staff share devices. Sign out only via `signOutHere()` (`lib/sign-out.ts`: this device only + a full page load) and finish sign-in with `window.location.replace`, never `router.push` — Next's in-memory back/forward cache otherwise shows the previous user's screens on Back. Every signed-in layout renders `<SessionGuard userId={profile.id} />`; keep it on new ones.
- POS deals — Student 5% OR Member price OR Code OR Staff OR Manager, only one per order. Code (Oct 2026): a discount code from Admin → Settings → Discount codes (`promo_codes`, Rs off or % off, min order, max uses, expiry in Nepal time) — the same codes work at online checkout; lookup, rules and the conditional use count are `lib/promo-codes.ts` (shared by `createOrder` and `createPosOrder`), the maths `codeDiscount()` in `lib/discounts.ts`; the POS labels it "Code MOMO30" and saves `orders.promo_code_id` (`lib/discounts.ts`, shared by the POS screen and `createPosOrder`, which recomputes everything; the screen only asks). Student: 5% off items with `products.student_discount_eligible` (Coca-Cola is off by default), whole rupees. Member: items with `products.member_price` (every momo is Rs 99, migration 022; set per item in Admin → Menu) charge that instead — but only with the member's card (migration 041): tapping Member asks for the LAST 3 DIGITS of the card number (`checkMemberCard`, matching in `lib/member-card.ts`: digits only, padded, so "45667" is 667), `createPosOrder` re-checks the `member_card` it's sent and saves `orders.membership_id` + `member_card` (shown in order details, the Excel, the order-placed popup), and Admin → Members shows how often each card was used. Staff (migration 035): up to `app_settings.staff_free_items` items cost Rs 0 — set in Admin → Settings → Staff sale (`updateStaffSale`, 0–20, 0 hides the button); `staffFreeItems()` frees the dearest first, never membership cards, and charges anything over the limit; tiles show Rs 0 while free items are left. Order lines keep the normal price either way; the saving is `orders.discount_amount` + `discount_label` ("Student 5%" / "Member price" / "Staff"). Staff free items show in the POS "Today" sheet under Discounts given and are left out of Marketing's "offers given" (a staff cost, not an offer).
- POS Manager discount (migration 038): a 4th deal, shown only once someone is a manager (`training_people.is_manager`, "Make manager" in Admin → Staff Hours → POS staff · PINs; `hasManager()`, `lib/manager-pin.ts`). Tapping Manager asks for a manager's OWN PIN (`checkManagerPin`; 5 wrong in 15 min locks, `MANAGER_PIN_FAIL`); then every item in the sale is Rs 0 (tiles and cart) EXCEPT frozen items (`products.is_frozen`, "Frozen item" in Admin → Menu — the two 55 Pcs momo packs) and membership cards (`managerFreeItems()` in `lib/discounts.ts`). `createPosOrder` re-checks the PIN it's sent (`manager_pin`), labels the discount "Manager" and saves `orders.discount_approved_by` (shown in order details and the Excel). The approval lasts for that one sale. Manager free sales show in the POS Today sheet's discounts and are left out of Marketing's "offers given".
- Half plates (POS only, migration 041; owner's call): an item with `products.half_price` (Admin → Menu "Half plate price"; blank = none, never on membership cards) can be sold as 1½, 2½ … plates — the "½" on its tile / "+ ½ plate" on its cart line adds ONE extra half to a line that already has a whole plate; a half is never sold on its own. The extra half is its own order line (`halfPlateName()` → "… (half plate)", `order_items.portion = 0.5`, so `stock_levels()` counts half a plate) at `halfPlatePrice()` (never more than a whole plate). Member price never applies to the half; student 5% does; staff/manager count it as one item. The screen and `createPosOrder` build the same line list (whole plates, then the half) — keep them in step (`lib/discounts.ts`).

- Security hardening (migration 040, Oct 2026 audit): a signed-in user can update ONLY `invite_accepted_at` on their own profile through the API — the `profiles_privilege_guard` trigger resets every other column, so any new profile field a user edits must go through a validated server action (service role). `addresses` (written from the browser) has DB checks: label ≤30, address 1–300 chars, pin inside Nepal or none.
